# 体系的デバッグ

## 概要

ランダムな修正は時間を無駄にし、新しいバグを生み出す。クイックパッチは根本的な問題を隠す。

**コアプリンシパル:** 修正を試みる前に常に根本原因を見つける。症状の修正は失敗。

**このプロセスの文字通りの違反は、精神的な違反。**

## 鉄則

```
根本原因を調査せずに修正してはならない
```

フェーズ 1 を完了していなければ、修正を提案できない。

## 使用タイミング

以下の技術的問題すべてに使用:
- テストの失敗
- 本番のバグ
- 予期しない動作
- パフォーマンス問題
- ビルドの失敗
- 統合の問題

**特にこのような場合に使用:**
- 時間プレッシャー下（緊急時は推測が誘惑される）
- 「たった一つの素早い修正」が明白に見える場合
- すでに複数の修正を試みた場合
- 前の修正が機能しなかった場合
- 問題を完全に理解していない場合

## 4 つのフェーズ

各フェーズを完了してから次に進むこと。

### フェーズ 1: 根本原因の調査

**修正を試みる前に:**

1. **エラーメッセージを注意深く読む**
   - エラーや警告を読み飛ばさない
   - しばしば正確な解決策が含まれている
   - スタックトレースを最後まで読む
   - 行番号、ファイルパス、エラーコードをメモする

2. **一貫して再現する**
   - 確実にトリガーできるか？
   - 正確なステップは何か？
   - 毎回発生するか？
   - 再現不可能であれば — より多くのデータを集める、推測しない

3. **最近の変更を確認する**
   - これを引き起こした可能性のある変更は何か？
   - git diff、最近のコミット
   - 新しい依存関係、設定変更
   - 環境の違い

4. **複数コンポーネントシステムで証拠を集める**

   **システムに複数のコンポーネントがある場合（CI → ビルド → 署名、API → サービス → データベース）:**

   **修正を提案する前に、診断計装を追加する:**
   ```
   各コンポーネント境界について:
     - コンポーネントに入るデータをログに記録
     - コンポーネントから出るデータをログに記録
     - 環境/設定の伝播を確認
     - 各レイヤーで状態を確認

   一度実行して、どこで壊れているかの証拠を集める
   次に証拠を分析して失敗しているコンポーネントを特定する
   次にその特定のコンポーネントを調査する
   ```

5. **データフローをトレースする**

   エラーがコールスタックの深い部分にある場合、`root-cause-tracing.md` を参照。

   **クイックバージョン:**
   - 悪い値はどこから来るのか？
   - 何がこれを悪い値で呼び出したのか？
   - 源まで遡り続ける
   - 症状ではなく源で修正する

### フェーズ 2: パターン分析

**修正する前にパターンを見つける:**

1. **動作する例を見つける**
   - 同じコードベースで動作する類似コードを探す
   - 壊れているものと類似して動作するものは何か？

2. **参考実装と比較する**
   - パターンを実装している場合は、参照実装を完全に読む
   - 斜め読みしない — すべての行を読む
   - パターンを完全に理解してから適用する

3. **違いを特定する**
   - 動作するものと壊れているものの違いは何か？
   - どんなに小さくても、すべての違いをリストアップする
   - 「これは関係ないはず」と仮定しない

4. **依存関係を理解する**
   - 他にどのコンポーネントが必要か？
   - 設定、環境は何が必要か？
   - どのような前提があるか？

### フェーズ 3: 仮説とテスト

**科学的手法:**

1. **単一の仮説を立てる**
   - 明確に述べる: 「X が根本原因だと思う。なぜなら Y」
   - 書き留める
   - 具体的に、曖昧でなく

2. **最小限にテストする**
   - 仮説をテストするために可能な限り小さな変更をする
   - 一度に一つの変数
   - 同時に複数のことを修正しない

3. **続ける前に確認する**
   - 機能したか？ Yes → フェーズ 4
   - 機能しなかった？ 新しい仮説を立てる
   - さらに修正を追加しない

4. **分からない時**
   - 「X を理解していない」と言う
   - 知ったふりをしない
   - 助けを求める
   - さらに調査する

### フェーズ 4: 実装

**症状ではなく根本原因を修正する:**

1. **失敗するテストケースを作成する**
   - 可能な限り単純な再現
   - 可能であれば自動化テスト
   - `test-driven-development` スキルを使って適切な失敗テストを書く

2. **単一の修正を実装する**
   - 特定された根本原因に対処する
   - 一度に一つの変更
   - 「ついでに」の改善なし
   - 付随したリファクタリングなし

3. **修正を検証する**
   - テストがパスするか？
   - 他のテストが壊れていないか？
   - 問題が実際に解決されたか？

4. **修正が機能しない場合**
   - STOP
   - カウント: 何回修正を試みたか？
   - 3 回未満: フェーズ 1 に戻り、新しい情報で再分析
   - **3 回以上: STOP してアーキテクチャを問い直す（以下の Step 5）**
   - 4 回目の修正を試みない。アーキテクチャの議論なしに

5. **3 回以上失敗した場合: アーキテクチャを問い直す**

   **アーキテクチャ的問題を示すパターン:**
   - 各修正が異なる場所で新しい共有状態/結合/問題を明らかにする
   - 修正に「大規模なリファクタリング」が必要
   - 各修正が他の場所に新しい症状を作る

   **基本的な前提を STOP して問い直す:**
   - このパターンは根本的に健全か？
   - 単なる惰性でそれを続けているのか？
   - 症状を修正し続けるより、アーキテクチャをリファクタリングすべきか？

   **さらに修正を試みる前にパートナーと議論する**

## Red Flags — STOP してプロセスに従う

以下を考えていたら:
- 「今は素早い修正、後で調査」
- 「X を変えてみて機能するか見る」
- 「複数の変更を追加してテストを実行する」
- 「テストをスキップして手動で確認する」
- 「おそらく X だ、それを修正しよう」
- 「完全には理解していないが、これが機能するかもしれない」
- 修正を提案する前にデータフローをトレースする
- **「もう一回修正を試みる」（すでに 2 回試みた場合）**
- **各修正が異なる場所に新しい問題を明らかにする**

**これらはすべて: STOP。フェーズ 1 に戻る。**

**3 回以上失敗した場合:** アーキテクチャを問い直す（フェーズ 4.5 参照）

## 一般的な言い訳

| 言い訳 | 実態 |
|--------|------|
| 「問題は単純、プロセスは不要」 | 単純な問題も根本原因がある。プロセスは単純なバグには高速。 |
| 「緊急事態、プロセスの時間なし」 | 体系的デバッグは推測より高速。 |
| 「まずこれを試して、次に調査する」 | 最初の修正がパターンを設定する。最初から正しくやる。 |
| 「修正を確認してからテストを書く」 | 未テストの修正は定着しない。テストが先。 |
| 「複数の修正で時間を節約」 | 何が機能したか分離できない。新しいバグを引き起こす。 |
| 「問題が分かった、修正しよう」 | 症状を見ること ≠ 根本原因を理解すること。 |
| 「もう一回修正を試みる」（2 回以上失敗後）| 3 回以上の失敗 = アーキテクチャの問題。パターンを問い直す。 |

## サポートファイル

- **`root-cause-tracing.md`** — バグをコールスタックを通じて後方にトレースして元のトリガーを見つける
- **`defense-in-depth.md`** — 根本原因を見つけた後に複数のレイヤーでバリデーションを追加する
- **`condition-based-waiting.md`** — 任意のタイムアウトを条件ポーリングに置き換える
