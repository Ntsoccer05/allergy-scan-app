# スキルを書く

## 概要

**スキルを書くことは、プロセスドキュメントに適用されたテスト駆動開発。**

**個人スキルは `.claude/skills/` に置く。**

テストケース（サブエージェントを使ったプレッシャーシナリオ）を書き、失敗するのを見て（ベースライン動作）、スキルを書いて（ドキュメント）、テストがパスするのを見て（エージェントが準拠する）、リファクタリングする（ループホールを閉じる）。

**コアプリンシパル:** スキルなしでエージェントが失敗するのを見ていなければ、スキルが正しいことを教えているか分からない。

**必要な背景:** このスキルを使う前に `test-driven-development` を理解すること。

## スキルとは何か

**スキル**は実証済みの技術、パターン、ツールのリファレンスガイド。将来の Claude インスタンスが効果的なアプローチを見つけて適用するのを助ける。

**スキルは:** 再利用可能な技術、パターン、ツール、リファレンスガイド

**スキルではない:** 一度問題を解決した方法についての物語

## TDD のスキルへのマッピング

| TDD コンセプト | スキル作成 |
|-------------|-----------|
| **テストケース** | サブエージェントを使ったプレッシャーシナリオ |
| **プロダクションコード** | スキルドキュメント（SKILL.md）|
| **テストが失敗（RED）** | エージェントがスキルなしでルールに違反する（ベースライン）|
| **テストがパス（GREEN）** | エージェントがスキルありで準拠する |
| **リファクタリング** | ループホールを閉じながら準拠を維持 |

## いつスキルを作成するか

**作成する場合:**
- 技術が直感的に明白でなかった
- プロジェクトをまたいで参照する
- パターンが広く適用できる（プロジェクト固有でない）
- 他の人に利益をもたらす

**作成しない場合:**
- 一度限りの解決策
- 他で十分に文書化された標準的な実践
- プロジェクト固有の規約（CLAUDE.md に置く）
- 機械的な制約（正規表現/バリデーションで強制できるなら自動化する）

## ディレクトリ構成

```
.claude/skills/
  skill-name/
    SKILL.md              # メインリファレンス（必須）
    supporting-file.*     # 必要な場合のみ
```

## SKILL.md の構成

**フロントマター（YAML）:**
- 必須フィールド: `name` と `description`（最大 1024 文字）
- `name`: 文字、数字、ハイフンのみ（括弧、特殊文字なし）
- `description`: 三人称、使用するタイミングのみを説明
  - 「Use when...」で始まる
  - 特定の症状、状況、コンテキストを含む
  - **スキルのプロセスやワークフローを絶対に要約しない**
  - 可能であれば 500 文字以下

```markdown
---
name: skill-name-with-hyphens
description: Use when [specific triggering conditions and symptoms]
---

# スキル名

## 概要
これは何か？1〜2 文でコアプリンシパル。

## 使用タイミング
[判断が明白でない場合のみ小さなフローチャート]

## コアパターン
Before/after コード比較

## クイックリファレンス
一般的な操作のテーブルまたは箇条書き

## 一般的なミス
何が間違うか + 修正

## Red Flags
STOP すべき思考パターン
```

## Claude 検索最適化（CSO）

**発見に重要:** 将来の Claude があなたのスキルを見つける必要がある

### 豊富な description フィールド

**目的:** Claude は description を読んで、特定のタスクにどのスキルをロードするかを決定する。

**形式:** 「Use when...」で始める

**重要: description = 使用タイミング、スキルの内容ではない**

description はトリガー条件のみを記述すること。スキルのプロセスやワークフローを要約しない。

```yaml
# ❌ 悪い: ワークフローを要約 — Claude はこれに従い、スキルを読み飛ばすかもしれない
description: Use when executing plans - dispatches subagent per task with code review between tasks

# ✅ 良い: トリガー条件のみ、ワークフロー要約なし
description: Use when executing implementation plans with independent tasks in the current session
```

### キーワードカバレッジ

Claude が検索するであろう言葉を使う:
- エラーメッセージ: "Hook timed out"、"race condition"
- 症状: "flaky"、"hanging"、"zombie"
- ツール: 実際のコマンド、ライブラリ名、ファイルタイプ

## 鉄則（TDD と同じ）

```
失敗するテストなしにスキルを作成してはならない
```

これは新しいスキルにも既存のスキルの編集にも適用される。

テストする前にスキルを書いた？ 削除する。最初からやり直す。

## スキル作成チェックリスト（TDD 適応）

**RED フェーズ — 失敗するテストを書く:**
- [ ] プレッシャーシナリオを作成する（規律スキルには 3 つ以上の組み合わせプレッシャー）
- [ ] スキルなしでシナリオを実行 — ベースライン動作を記録する
- [ ] 言い訳/失敗のパターンを特定する

**GREEN フェーズ — 最小限のスキルを書く:**
- [ ] name は文字、数字、ハイフンのみ
- [ ] YAML フロントマターに必須の `name` と `description` フィールド
- [ ] description が「Use when...」で始まり、特定のトリガー/症状を含む
- [ ] description が三人称で書かれている
- [ ] 検索のためにキーワードを全体に配置
- [ ] 概要とコアプリンシパルを明確に
- [ ] RED で特定した特定の失敗に対処
- [ ] スキルありでシナリオを実行 — エージェントが準拠することを確認

**REFACTOR フェーズ — ループホールを閉じる:**
- [ ] テストから新しい言い訳を特定する
- [ ] 明示的なカウンターを追加する（規律スキルの場合）
- [ ] すべてのテストイテレーションから言い訳テーブルを構築する
- [ ] Red Flags リストを作成する
- [ ] 完璧になるまで再テストする

**デプロイ:**
- [ ] スキルを git にコミット
