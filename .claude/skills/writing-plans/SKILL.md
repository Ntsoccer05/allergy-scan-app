# 実装計画を書く

## 概要

コードベースについてゼロから始める開発者を想定して、包括的な実装計画を書く。各タスクで触るファイル、コード、テスト、確認すべきドキュメント、テスト方法を文書化する。一口サイズのタスクとして計画全体を提供する。DRY。YAGNI。TDD。頻繁なコミット。

開発者はスキルがあるが、このツールセットや問題ドメインについてはほぼ何も知らないと想定。良いテスト設計もあまり知らないと想定。

**開始時に宣言:** 「writing-plans スキルを使って実装計画を作成します。」

**プランの保存先:** `.claude/plans/pending/YYYY-MM-DD-<feature-name>.md`

## スコープチェック

仕様が複数の独立したサブシステムをカバーしている場合、brainstorming 中にサブプロジェクトの仕様に分解されているべき。そうなっていなければ、計画を分割することを提案する — サブシステムごとに一つ。各計画は単独でテスト可能なソフトウェアを生み出すべき。

## ファイル構成

タスクを定義する前に、作成または変更するファイルをマップし、各ファイルの責任を明確にする。

- 明確な境界と明確に定義されたインターフェースを持つユニットを設計
- 一度に把握できるコードをうまく推論できる。ファイルが小さく集中しているほど、編集がより確実
- 一緒に変更されるファイルは一緒に置く。技術的な層ではなく責任で分割
- 既存のコードベースでは確立されたパターンに従う

## タスクの粒度（一口サイズ）

**各ステップは一つのアクション（2〜5分）:**
- 「失敗するテストを書く」— ステップ
- 「それが失敗することを確認するために実行する」— ステップ
- 「テストをパスさせる最小限のコードを実装する」— ステップ
- 「テストを実行してパスすることを確認する」— ステップ
- 「コミットする」— ステップ

## 計画ドキュメントのヘッダー

**すべての計画はこのヘッダーで始めること:**

```markdown
# [機能名] 実装計画

> **エージェント向け:** REQUIRED SUB-SKILL: `executing-plans` または `subagent-driven-development` を使ってこの計画をタスクごとに実装すること。ステップはチェックボックス構文（`- [ ]`）で追跡。

**目標:** [何を作るか一文で説明]

**アーキテクチャ:** [アプローチについて 2〜3 文]

**技術スタック:** [主要な技術・ライブラリ]

---
```

## タスク構成

````markdown
### Task N: [コンポーネント名]

**Files:**
- Create: `exact/path/to/file.ts`
- Modify: `exact/path/to/existing.ts:123-145`
- Test: `exact/path/to/test.ts`

- [ ] **Step 1: 失敗するテストを書く**

```typescript
describe('specificBehavior', () => {
  it('should do something specific', () => {
    const result = functionUnderTest(input);
    expect(result).toBe(expected);
  });
});
```

- [ ] **Step 2: テストが失敗することを確認する**

Run: `pnpm --filter <package> test path/to/test`
Expected: FAIL with "function not defined"

- [ ] **Step 3: 最小限の実装を書く**

```typescript
export function functionUnderTest(input: Input): Output {
  return expected;
}
```

- [ ] **Step 4: テストがパスすることを確認する**

Run: `pnpm --filter <package> test path/to/test`
Expected: PASS

- [ ] **Step 5: コミット**

```bash
git add path/to/test.ts path/to/file.ts
git commit -m "feat: add specific feature"
```
````

## プレースホルダー禁止

開発者が必要とする実際のコンテンツを各ステップに含めること。以下は**計画の失敗** — 絶対に書かない:
- "TBD"、"TODO"、"後で実装"、"詳細を記入"
- 「適切なエラーハンドリングを追加」/「バリデーションを追加」/「エッジケースを処理」
- 「上記のテストを書く」(実際のテストコードなし)
- 「Task N と同様」(コードを繰り返す — 開発者はタスクを順不同で読む場合がある)
- 方法を示さずに何をするかを説明するステップ（コードステップにはコードブロックが必要）
- どのタスクでも定義されていない型、関数、メソッドへの参照

## 記憶すること
- 常に正確なファイルパス
- すべてのステップに完全なコード — ステップがコードを変更するなら、コードを示す
- 期待される出力を伴う正確なコマンド
- DRY、YAGNI、TDD、頻繁なコミット
- テストコマンドは `pnpm` を使用（このプロジェクトの標準）

## セルフレビュー

完全な計画を書いた後、仕様を新鮮な目で確認し、計画を照合する。

**1. 仕様カバレッジ:** 仕様の各セクション/要件を確認。それを実装するタスクを指摘できるか？ギャップをリストアップ。

**2. プレースホルダースキャン:** 「プレースホルダー禁止」セクションのパターンで計画を検索。修正する。

**3. 型一貫性:** 後のタスクで使う型、メソッドシグネチャ、プロパティ名は、前のタスクで定義したものと一致しているか？

問題があればインラインで修正する。仕様要件に対応するタスクがなければ、タスクを追加する。

## 実行の引き渡し

計画を保存した後、実行の選択肢を提示:

**「計画を `.claude/plans/pending/<filename>.md` に保存しました。実行方法を選んでください:**

**1. サブエージェント駆動（推奨）** — タスクごとに新しいサブエージェントを派遣、タスク間でレビュー、高速なイテレーション

**2. インライン実行** — このセッション内で `executing-plans` を使って実行、チェックポイントでのバッチ実行

**どちらにしますか？」**

**サブエージェント駆動を選択した場合:**
- **REQUIRED SUB-SKILL:** `subagent-driven-development` を使用

**インライン実行を選択した場合:**
- **REQUIRED SUB-SKILL:** `executing-plans` を使用
