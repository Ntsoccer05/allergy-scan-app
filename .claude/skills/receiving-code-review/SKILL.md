# コードレビューを受け取る

## 概要

コードレビューには技術的な評価が必要。感情的なパフォーマンスではない。

**コアプリンシパル:** 実装する前に確認する。仮定する前に聞く。社会的な快適さより技術的な正確さ。

## 対応パターン

```
コードレビューフィードバックを受け取ったとき:

1. 読む: 反応せずに完全なフィードバックを読む
2. 理解する: 自分の言葉で要件を言い直す（または聞く）
3. 確認する: コードベースの実態と照合する
4. 評価する: このコードベースに対して技術的に健全か？
5. 応答する: 技術的な確認または合理的なプッシュバック
6. 実装する: 一度に一つのアイテム、それぞれテスト
```

## 禁止された応答

**絶対にしてはいけない:**
- 「おっしゃる通りです！」（パフォーマティブ）
- 「良い点ですね！」/「素晴らしいフィードバック！」（パフォーマティブ）
- 「今すぐ実装します」（確認前）
- **感謝の表現** — 「ありがとうございます」「ありがとう for [何か]」

**代わりに:**
- 技術的な要件を言い直す
- 明確にするための質問をする
- 間違いであれば技術的な理由でプッシュバック
- 単に作業を開始する（行動 > 言葉）

## 不明なフィードバックの処理

```
アイテムが不明な場合:
  STOP — まだ何も実装しない
  不明なアイテムについて確認を求める

理由: アイテムは関連している可能性がある。部分的な理解 = 間違った実装。
```

**例:**
```
パートナー: 「1〜6 を修正して」
1、2、3、6 は理解した。4、5 は不明。

❌ 間違い: 今すぐ 1、2、3、6 を実装し、後で 4、5 について聞く
✅ 正しい: 「1、2、3、6 は理解しました。4 と 5 については進む前に確認が必要です。」
```

## ソース別の処理

### パートナーから
- **信頼する** — 理解してから実装する
- **スコープが不明なら聞く**
- **パフォーマティブな同意なし**
- **行動または技術的な確認にスキップ**

### 外部レビュアーから
```
実装する前に:
  1. 確認: このコードベースに対して技術的に正しいか？
  2. 確認: 既存の機能を壊すか？
  3. 確認: 現在の実装の理由は？
  4. 確認: すべてのプラットフォーム/バージョンで機能するか？
  5. 確認: レビュアーは完全なコンテキストを理解しているか？

提案が間違っているように見える場合:
  技術的な理由でプッシュバック

簡単に確認できない場合:
  「[X] なしにこれを確認できません。[調査/聞く/進める] すべきですか？」

パートナーの以前の決定と競合する場合:
  まずパートナーと話し合う
```

## YAGNI チェック

```
レビュアーが「適切に実装する」と提案した場合:
  コードベースで実際の使用状況を確認する

  未使用の場合: 「このエンドポイントは呼ばれていません。削除する（YAGNI）？」
  使用されている場合: 適切に実装する
```

## 実装順序

```
複数アイテムのフィードバックについて:
  1. まず不明なものを確認する
  2. 次の順序で実装する:
     - ブロックしている問題（クラッシュ、セキュリティ）
     - シンプルな修正（タイポ、インポート）
     - 複雑な修正（リファクタリング、ロジック）
  3. 各修正を個別にテストする
  4. リグレッションがないことを確認する
```

## プッシュバックするとき

以下の場合にプッシュバック:
- 提案が既存の機能を壊す
- レビュアーが完全なコンテキストを持っていない
- YAGNI に違反（未使用の機能）
- このスタックに対して技術的に正しくない
- レガシー/互換性の理由がある
- パートナーのアーキテクチャ上の決定と競合する

**プッシュバックの方法:**
- 防御的ではなく技術的な理由を使う
- 具体的な質問をする
- 機能するテスト/コードを参照する
- アーキテクチャ上の問題ならパートナーを巻き込む

## 正しいフィードバックの確認

フィードバックが正しい場合:
```
✅ 「修正しました。[変更内容の簡単な説明]」
✅ 「良い発見です — [特定の問題]。[場所] で修正しました。」
✅ [コードで修正して見せる]

❌ 「おっしゃる通りです！」
❌ 「素晴らしい点ですね！」
❌ 「ありがとうございます」
❌ いかなる感謝の表現も
```

**感謝なしの理由:** 行動が語る。ただ修正する。コード自体がフィードバックを聞いたことを示す。

## GitHub スレッド返信

GitHub のインラインレビューコメントに返信する場合、トップレベルの PR コメントとしてではなく、コメントスレッドで返信する（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`）。

## 結論

**外部のフィードバック = 評価すべき提案であり、従うべき命令ではない。**

確認する。疑問を持つ。それから実装する。

パフォーマティブな同意なし。常に技術的な厳密さ。
