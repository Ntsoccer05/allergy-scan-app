# データベース設計原則

## 正規化方針（第1〜第5正規形）

テーブル設計は原則として**第5正規形（5NF）**を目標とする。
ただし JOIN コストがシステム要件に照らして許容不能と判断した場合は、意図的に非正規化してよい（必ずコメントで理由を明記する）。

### 各正規形の要件

| 正規形 | 要件 | チェック観点 |
|-------|------|------------|
| 1NF | 繰り返しグループなし・属性値は原子値 | 配列型・CSV 格納・行番号で区別される列がないか |
| 2NF | 部分関数従属の排除（複合キーの一部にしか依存しない属性を別テーブルへ） | 複合 PK のテーブルで単一 PK 列にしか依存しない列がないか |
| 3NF | 推移的関数従属の排除（非キー属性が別の非キー属性を決定しない） | `A → B → C` の連鎖がないか |
| BCNF | すべての決定項が候補キー（3NF の強化版） | 非候補キー属性が他の属性を決定していないか |
| 4NF | 多値従属の排除（独立した複数の多値関係を 1 テーブルに混在させない） | M:N 関係が複数混在していないか |
| 5NF | 結合従属の排除・無損失分解（分割したテーブルを SQL で結合したとき元のデータが完全に復元できる） | 3 テーブル以上の結合を要する属性関係がないか |

### 無損失分解の確認方法

分割前後で以下を満たすこと:

```sql
-- 分割後テーブルを JOIN して分割前の行数・値と一致すること
SELECT COUNT(*) FROM a JOIN b ON a.key = b.key
-- = SELECT COUNT(*) FROM original_table
```

## 非正規化を許容するケース（意図的な例外）

以下の条件を **両方** 満たす場合のみ非正規化を採用する:

1. JOIN によるクエリコストが測定可能な形で問題になる（またはなることが明確に予測できる）
2. 非正規化の理由・影響範囲・更新時の整合性保持方法をコメントに明記する

```sql
-- ✅ 許容例: scan_histories.detected は products.allergens の派生値だが
--    1スキャンに1回しか書かれず更新されない snapshot として保存するため非正規化を許容
detected JSON DEFAULT '[]'
```

## このプロジェクトの現行テーブルにおける設計判断

| テーブル・カラム | 正規形的懸念 | 採用理由 |
|--------------|-----------|---------|
| `products.allergens` (JSONB) | 1NF 違反相当（配列埋め込み） | OCR スキャンのたびに UPSERT する高頻度書き込みで JOIN コストが問題になるため。スナップショット的な用途 |
| `users.allergies` (JSONB) | 1NF 違反相当（動的キー） | アレルゲン品目は追加・廃止が起きるマスターデータ。正規化すると品目追加のたびにカラム追加マイグレーションが必要になるため |
| `scan_histories.detected` (JSONB) | 派生データの重複保存 | スキャン時点のアレルゲン設定による snapshot（後から設定が変わっても履歴は変わらないようにする設計意図） |
| `scan_histories.location` (JSONB) | 1NF 違反相当 | 店舗情報は外部 API から取得したアドホックな値で、`stores` テーブルを持つほどの参照頻度・整合性要件がないため |

## カラム追加・テーブル分割のガイドライン

### カラムを追加するとき

1. 追加するカラムが **既存の PK / 候補キーのみ**に関数従属しているか確認する
2. 既存カラムへの推移的従属（`A → B → C` で C を追加しようとしている）なら、`B` を PK に持つ別テーブルを先に作る
3. NULL 許容・DEFAULT 付きで追加し、ダウンタイムなしで適用できることを確認する（`implementation_rules.md` のマイグレーション制約も参照）

### テーブルを分割するとき

1. 分割後テーブルを結合したとき元のデータが完全に復元できること（無損失分解）を SQL で検証する
2. 既存インデックスが分割後テーブルでも有効か確認する（`implementation_rules.md` の必須インデックス一覧も参照）
3. 分割によって `JOIN` が増える箇所を列挙し、クエリプランを確認する（`EXPLAIN ANALYZE`）

## アンチパターン

```sql
-- ❌ 複数値をカンマ区切りで1列に格納（1NF 違反）
allergens TEXT DEFAULT 'egg,milk,wheat'

-- ❌ 同一ファクト（商品名）が複数テーブルに重複保存（更新異常リスク）
-- products.product_name と scan_histories.product_name を独立して UPDATE している
-- → scan_histories.product_name はスキャン時点の snapshot として意図的に保持する場合のみ許容

-- ❌ 非キー属性が別の非キー属性を決定（3NF 違反例）
-- products テーブルに store_address を追加し、store_address が store_name に依存する場合
-- → stores テーブルを分離して products / scan_histories から FK 参照する
```
